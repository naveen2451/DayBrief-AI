# Milestone 9 — Unified DayBrief AI Runner

**Project:** DayBrief AI  
**Technology:** TypeScript, Node.js, Microsoft Foundry, Azure OpenAI Responses API  
**Status:** Completed

## 1. Objective

Build a unified AI agent runner that retrieves information from four integrations and generates a personalised daily briefing.

The integrations are:

1. **Weather:** Live weather information for High Wycombe using Foundry Web Search.
2. **Outlook Emails:** Retrieve and summarise the five latest emails using Microsoft Graph.
3. **Outlook Calendar:** Retrieve today's calendar events using Microsoft Graph.
4. **GitHub:** Retrieve open pull requests using GitHub MCP.

The final response should contain five sections:

- Weather
- Outlook Emails
- Calendar
- GitHub
- Action Items

The briefing should be concise, accurate and under 250 words.

## 4. Initial Foundry Request

The runner creates a conversation and sends the briefing instructions.

```ts
const conversation = await openai.conversations.create();

let response = await openai.responses.create({
  conversation: conversation.id,
  input: prompt,
  tool_choice: "required",
  parallel_tool_calls: false,
  max_output_tokens: 7000,
});
```

### Important parameters

**`conversation`**

Maintains the conversation history across requests.

**`input`**

Contains the user's briefing instructions.

**`tool_choice: "required"`**

Requires the agent to request at least one tool rather than immediately returning a text response.

It does not guarantee that all four integrations will execute.

**`parallel_tool_calls: false`**

Requests sequential tool calling, making the execution flow easier to control and debug.

**`max_output_tokens`**

Limits the tokens generated by the model for that response.

## 5. Function-Calling Loop

The most important part of this milestone is the orchestration loop.

Simplified implementation:

```ts
const MAX_TOOL_ROUNDS = 6;

for (let round = 0; round < MAX_TOOL_ROUNDS; round++) {
  const calls = response.output.filter(isFunctionCall);

  if (calls.length === 0) {
    break;
  }

  const outputs = [];

  for (const call of calls) {
    let result;

    switch (call.name) {
      case "get_outlook_emails":
        result = await getOutlookEmails(5);
        break;

      case "get_outlook_calendar_events":
        result = await getOutlookCalendarEvents(startDate, endDate);
        break;

      default:
        throw new Error(`Unexpected function: ${call.name}`);
    }

    outputs.push({
      type: "function_call_output",
      call_id: call.call_id,
      output: JSON.stringify(result),
    });
  }

  response = await openai.responses.create({
    conversation: conversation.id,
    input: outputs,
    parallel_tool_calls: false,
    max_output_tokens: 3000,
  });
}
```

This example illustrates the orchestration pattern. The actual runner also parses function arguments, tracks integration execution and caches tool results.

### Outer loop

```ts
for (let round = 0; round < 6; round++)
```

The outer loop continues the interaction between Node.js and Foundry.

Each iteration:

1. Reads the latest Foundry response.
2. Identifies pending custom function calls.
3. Executes the requested functions.
4. Sends the function outputs back to Foundry.
5. Waits for the next response.

The value `6` is an application-defined safety limit, not a Microsoft Foundry requirement.

### Inner loop

```ts
for (const call of calls)
```

The inner loop executes every custom function requested in the current Foundry response.

Foundry does not necessarily identify every function it will need in the initial response. It can request additional functions after receiving earlier results.

### Why the response changes

```ts
response = await openai.responses.create({
  conversation: conversation.id,
  input: outputs,
});
```

This statement replaces the previous value of `response` with the latest response from Foundry.

Consequently, the next outer-loop iteration processes the new response rather than the original one.

### Loop termination

```ts
if (calls.length === 0) {
  break;
}
```

The loop stops when there are no pending custom function calls.

The runner also checks for unfinished function calls after reaching the maximum number of rounds.

## 6. Tool Result Caching

During testing, Foundry sometimes requested the same Outlook function more than once.

To avoid repeated Microsoft Graph requests, a cache was introduced:

```ts
const toolResultCache = new Map<string, string>();

const cacheKey = `${call.name}:${call.arguments}`;

let output = toolResultCache.get(cacheKey);

if (output === undefined) {
  // Execute the function.
  // Serialise its result.
  // Store the result in the cache.
}
```

### Benefits

- Reduces unnecessary Microsoft Graph requests.
- Avoids retrieving identical data repeatedly.
- Reduces latency and repeated backend work.

The cache is local to one `runDayBrief()` execution.

## 7. Integration Execution Tracking

The runner tracks whether Outlook integrations were executed:

```ts
emailCalled = true;
calendarCalled = true;
```

It also records response output types:

```ts
outputTypes.push(...response.output.map((item) => item.type));
```

These values are returned alongside the final briefing:

```ts
export type DayBriefResult = {
  summary: string;
  emailCalled: boolean;
  calendarCalled: boolean;
  outputTypes: string[];
};
```

The integration test uses these values to check:

- Outlook email execution
- Outlook calendar execution
- GitHub MCP activity
- Web Search activity

**Important:** Observing `mcp_call` or `web_search_call` confirms tool activity, but does not by itself prove that useful data was successfully retrieved.

## 8. Key Debugging Issue and Resolution

### Problem

The runner encountered the following error:

```text
400 No tool output found for function call call_...
```

Initially, possible causes included:

- Duplicate function calls
- Incorrect `call_id`
- Conversation ID mismatch
- Parallel tool execution
- Foundry continuation behaviour

### Investigation

SDK debug logging was enabled to inspect the actual HTTP request.

The application correctly constructed the function output, and the `call_id` matched.

However, the second HTTP request did not contain the `input` property.

### Root cause

The following property had accidentally been removed from the second `responses.create()` call:

```ts
input: outputs,
```

### Fix

```ts
response = await openai.responses.create({
  conversation: conversation.id,
  input: outputs,
  parallel_tool_calls: false,
  max_output_tokens: 3000,
});
```

After restoring `input: outputs`, function-call continuation worked again.

### Additional issue

Without an explicit tool requirement, the agent sometimes generated a response without executing any integrations.

The initial request was updated with:

```ts
tool_choice: "required",
```

This resolved the observed no-tool execution behaviour during testing.

## 10. Key Learnings

### AI agent orchestration

The model decides which tools it needs. The application executes custom functions and returns their results.

### Hosted vs custom tools

Hosted Web Search and GitHub MCP calls are managed by Foundry, while Outlook custom functions execute inside Node.js.

### Function-call continuation

Each custom function result must be returned with the corresponding `call_id`.

### Conversation state

The same conversation ID maintains the interaction across multiple Responses API requests.

### Safety limits

A maximum round count prevents unlimited custom function execution.

### Debugging

Inspecting the SDK's outgoing HTTP request can reveal issues that are not obvious from application-level logs.
